1) How dark mode works in this project

Tailwind config

Tailwind is configured with darkMode: 'class'. That means dark styles only activate when a parent element (typically <html>) has a dark class. 

// frontend/tailwind.config.js
export default {
  darkMode: 'class',
  // ...
}

In the built CSS, Tailwind generates selectors like: :is(.dark body){...} and :is(.dark .btn-secondary){...}.

Theme source of truth

The “theme state” is persisted in localStorage under theme (values: 'dark' or 'light'), and the UI toggles the dark class on document.documentElement. 

// frontend/src/components/ThemeToggle.tsx (simplified)
if (isDark) {
  document.documentElement.classList.add('dark');
  localStorage.setItem('theme', 'dark');
  document.documentElement.style.colorScheme = 'dark';
} else {
  document.documentElement.classList.remove('dark');
  localStorage.setItem('theme', 'light');
  document.documentElement.style.colorScheme = 'light';
}

color-scheme is important for native UI (scrollbars/form controls) to match the theme.

No-flash initialization

To avoid “light page loads then turns dark” (FOUC), this repo applies the theme before React mounts via a small script in frontend/index.html. 

<script>
(function () {
  const stored = localStorage.getItem('theme');
  const prefersDark = window.matchMedia('(prefers-color-scheme: dark)').matches;
  const shouldDark = stored === 'dark' || (stored === null && prefersDark);
  document.documentElement.classList.toggle('dark', shouldDark);
  document.documentElement.style.colorScheme = shouldDark ? 'dark' : 'light';
})();
</script>

Then ThemeToggle initializes from the existing <html class="dark"> state to prevent it from “undoing” the initial theme.

Where dark styles live

Dark styling is a mix of:

• Tailwind utility classes on components/pages (e.g. dark:bg-slate-900)
• shared component classes in frontend/src/index.css using @apply with dark: variants. 

@layer base {
  body {
    @apply bg-orange-50 dark:bg-slate-900 text-slate-800 dark:text-slate-100;
  }
}
Why you previously saw “dark flash then back to light”: the HTML script applied dark, but React-mounted code computed a different initial theme and removed the dark class. Fixing the initial state to follow the DOM resolves this.

3) How industry typically implements dark mode

Common goals

In production apps, dark mode is usually treated as a first-class “theme system”, not just a toggle:

• No flash (FOUC) on initial load
• Persisted preference (per user, often via cookie/server)
• Uses OS preference by default (prefers-color-scheme)
• Accessible contrast + consistent tokens
• Works in SSR/hydration (Next.js/Remix) without mismatches
• Optional: sync across tabs (storage events)

Two mainstream approaches

A) Class-based (like this repo): put a class on <html> and use either Tailwind dark variants or CSS selectors.

B) CSS variables (design tokens): set theme variables on :root or a theme container. UI uses var(--color-bg), var(--color-text), etc. 

/* Token-based */
:root { --bg: white; --text: black; }
:root[data-theme="dark"] { --bg: #0b1220; --text: #e6edf6; }

body { background: var(--bg); color: var(--text); }

Token-based theming scales better as the app grows because you update tokens, not every component.

SSR / server preferences

For SSR apps, industry often stores theme preference in a cookie and applies the theme class/attribute in server-rendered HTML so the first paint is correct. 

<html data-theme="dark">...server-rendered...</html>

Client-side code then reads the attribute and uses it as the initial state (same idea as we do here with the dark class).

Sync & observability

Larger apps commonly add:

• cross-tab sync: listen to window.addEventListener('storage', ...)
• analytics: theme adoption rates
• testing: visual regression across themes

4) Differences: this project vs industry standard

What’s already pretty good here:

• Uses darkMode: 'class' (predictable)
• Applies theme before React mounts (prevents FOUC)
• Sets color-scheme (better native widgets)

Main gaps vs many mature apps:

• No unified token system yet (many components still use explicit colors)
• No cross-tab sync (optional)
• No user profile persistence (server-side) (optional)
• No explicit “system” theme mode (light/dark/system) (optional)

5) Practical checklist (for this repo)

If dark mode “does nothing”

1) Confirm <html> gets the dark class. In DevTools Console: 

document.documentElement.classList.contains('dark')

2) Confirm Tailwind builds dark selectors (search built CSS for .dark).

3) Ensure components actually include dark: variants (or rely on token variables).

If you see a flash or reverts

1) Apply theme before React mounts (this repo does).

2) Make React theme state initialize from the already-applied DOM class/attribute.

3) Avoid multiple “sources of truth” fighting (DOM vs localStorage vs system) without a clear priority order.
